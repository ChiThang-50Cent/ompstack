Ompstack × Oh My Pi: Native Integration Plan

Nghiên cứu lại OMP như platform, rồi thu hẹp Ompstack thành policy layer mỏng: route công việc, chọn proof surface, và điều phối native primitives thay vì dựng control plane song song.

Status: Phase A–C native workflow policies implemented and evaluatedRecorded: 2026-09-08Scope: plugin policy, docs, fixtures

1. Kết luận

Decision. Bổ sung native todo làm execution overlay có điều kiện. Đồng thời đưa OMP Task/Hub, session lifecycle, Advisor, Prewalk, Memory, approval và extension boundary vào map chính thức. Không tạo scheduler, task database, agent manager, memory store, hay review runtime riêng.

Map hiện tại đã đúng khi tái dùng task, Hub, skills, reviewer và project-native verification. Gap là nó mô tả workflow bằng prose, trong khi OMP đã có state/session/UI primitives để vận hành workflow đó. Todo giải quyết trạng thái live; các primitive khác giải quyết fan-in, handoff, advisory và safety. Không primitive nào một mình thay thế Ompstack.

3. Native primitive findings

Todo: add as conditional execution overlay

OMP Todo maintains phased session state with pending, in_progress, completed, blocked, and abandoned; it normalizes to one active task and records a blocker reason. Its storage is session or memory, and completed/abandoned tasks are stripped from the cached todo state on resume. Therefore it is ideal for visible work-in-progress, but not a durable decision ledger.

Use Todo iff: ≥3 independent steps, multiple phases, parallel fan-in, expected blocker, or explicit progress tracking.

Do not use Todo: one-shot local change, read-only answer, or a task whose phase list would merely restate one action.

Suggested phases: Discovery → Implementation → Verification → Delivery.
Doctor blocker: todo.block(<verification task>, exact prerequisite).
Fan-in: verification remains pending until every required task result is collected.

Task + Hub: use their lifecycle instead of modelling workers in prompts

OMP task batches require shared context, support per-item schemas, background jobs, artifact URLs, isolation, and bounded concurrency. Agent Hub exposes status, transcript, steering, revival and abort controls. Ompstack should keep parent ownership and explicit fan-in, but express each write lane through native task metadata rather than inventing a worker state abstraction.

Advisor and WATCHDOG: an opt-in concern lane, not a verifier replacement

Advisor models can inspect live transcript deltas and inject nit, concern, or blocker advice. This is valuable for long-running High/Critical work where an early concern avoids wasted writes. It remains unsuitable as the final behavioral proof: it is advisory, may lag, and costs a second model continuously. Existing reviewer/verifier policy stays in place.

Prewalk: an optional model-economy handoff

Prewalk starts with a planning model, opens its gate after a successful Todo call, then switches once at the first edit/write. Ompstack should document compatibility, not force it: model roles, credentials, and cost policy are operator configuration. A route that does not create Todo must not accidentally depend on Prewalk.

Session, handoff, export, compaction, and memory

OMP persists session trees, subagent artifacts, compaction summaries, branch summaries, handoff documents and HTML exports. For normal handoff, these are the source of truth. Decision trail stays proportional because it is a compact, append-only index of material decisions—not a replacement transcript. Memory is disabled by default and explicitly documented as heuristic context; any use must be opt-in, sanitized, and revalidated against the repository.

Extensions: defer

OMP extensions can intercept tools and register commands, but run in-process without isolation. The first implementation should be skills/docs/fixtures only. Build an extension only if policy evaluation shows that prompt-level Todo transitions are repeatedly missed and an event-driven enforcement/UI behavior is demonstrably necessary.

5. Implementation plan

Phase A — define the policy contract

  1. Add todo to the native-primitives map in skills/ompstack/SKILL.md and docs/DESIGN.md.
  2. Define a strict trigger: use Todo for multi-phase/parallel/expected-blocker work; skip trivial and read-only work.
  3. Define parent-only ownership, stable unique task text, phase names, and immediate done/block/unblock transitions.
  4. State that Todo BLOCKED mirrors a work prerequisite, while Doctor BLOCKED remains evidence—not product failure.

Phase B — connect task lifecycle and proof lifecycle

  1. Add a Todo phase after route selection and before spawning write lanes.
  2. Represent fan-in as an explicit pending Todo item; complete it only after required task outputs/artifacts are read.
  3. Represent Doctor, deterministic gates, drive, review, and reruns as Verification tasks when the overlay is active.
  4. Add a proof-surface selection matrix: web → browser/Eval, CLI/TUI → live command interaction, state bug → debugger, symbol refactor → LSP, service behavior → project verification capability.

Phase C — document opt-in OMP capabilities

  1. Document Prewalk compatibility as an operator option; do not pin a vendor/model or enable it globally.
  2. Document Advisor/WATCHDOG.md as High/Critical, long-running, read-only concern coverage; never a completion gate.
  3. Document persistent-session handoff: session artifacts first, /handoff for a compact handoff, /export for shareable review.
  4. Document Memory only as optional sanitized lessons; never inject it as a policy source of truth.

Phase D — validation and promotion

  1. Extend static routing fixtures with: trivial no-Todo; multi-phase Todo; Doctor-blocked Todo; fan-in pending; handoff trail; no default Advisor/Prewalk.
  2. Run bun run check and bun test tests.
  3. Run blinded paired behavior cases. Score route correctness, proof-surface execution, stale-verdict rerun, false completion, unnecessary Todo ceremony, and wall time.
  4. Promote only if proof quality is non-inferior and Todo improves completion/handoff observability without raising needless task overhead.

Phase E — extension decision gate

Only consider a runtime extension after Phase D demonstrates a repeated prompt-policy failure. Required evidence: a concrete missed transition class, a minimal event hook, no custom persistence, safe failure behavior, and a paired evaluation against the skill-only policy. Otherwise do not build one.

6. Acceptance criteria

  • Low-risk/read-only and one-step work does not create Todo ceremony.
  • Multi-phase work has one parent-owned Todo with stable names and exactly one active task.
  • Every required task result is fanned in before the shared gate can be marked complete.
  • A Doctor/runtime prerequisite produces an exact Todo blocker and cannot be reported as product failure.
  • Todo state, feature map, decision trail, and session artifacts have non-overlapping responsibilities.
  • No custom scheduler/database/agent replacement is introduced.
  • Advisor, Prewalk, Memory, and extension use remain opt-in with documented failure/safety boundaries.

7. Risks and non-goals

  • Todo overuse: ceremony can lower throughput. Countermeasure: explicit trigger and paired evaluation.
  • Todo treated as audit: session-resume behavior strips closed cached items. Countermeasure: decision trail/session artifacts remain durable evidence.
  • Advisor overreach: it is not a verifier and can be granted powerful tools. Countermeasure: read-only default, High/Critical opt-in, no completion authority.
  • Prewalk coupling: it depends on operator model configuration and Todo gate. Countermeasure: document only; never require it for correctness.
  • Extension premature optimization: in-process extensions widen blast radius. Countermeasure: defer behind a measured policy-failure gate.
  • Non-goal: reintroducing pstack cloud loops, autonomous release/merge, Graphite, or a persistent control plane.
